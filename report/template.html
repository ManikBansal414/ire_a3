Setup

Data. SIFT-1M (128-d, Euclidean) and GloVe-100 (1,183,514 × 100, angular) from ann-benchmarks. GloVe vectors and queries are L2-normalised, so Euclidean distance ranks exactly like angular distance (‖a−b‖² = 2 − 2cos). Queries 0–4,999 are the tune half and 5,000–9,999 the test half. Selection rule. Every "at recall X" number is chosen on the tune half only: per build, the smallest efSearch/nprobe whose tune recall ≥ X; then the build with the highest tune QPS. Tables report that choice's test-half recall and QPS. Recall@10 is my own function: a returned id is a hit if its true distance (recomputed in float64 from the raw vectors, never the index's approximate distance) is ≤ the true 10th-neighbour distance, so ties at rank 10 are not mistakes; duplicates and −1 padding are handled (13 unit tests). Timing. One query per search call, FAISS and BLAS pinned to one thread, 50 warm-up queries, then {{num:n_reps}} repeats over {{num:n_timed}} test queries (each repeat cycles the queries for ≥ {{num:min_rep_s}} s); the median is reported. Builds use all {{num:threads}} hardware threads. Index size = bytes of faiss.serialize_index. Builds: HNSW M ∈ {8,16,32} (efConstruction 200); IVF nlist ∈ {{{num:nlist_set}}}; IVF-PQ m = d/4 sub-quantisers × 8 bits (32 B/code SIFT, 25 B/code GloVe).

One-at-a-time vs batch. A single query is a matrix–vector product: to answer it the CPU must stream the whole 512 MB (SIFT) database from RAM and does only one multiply-add per float loaded, so it is limited by memory bandwidth ({{num:sift_one_ms}} ms per query). A batch turns the work into a matrix–matrix product (BLAS GEMM): each block of database vectors brought into cache is reused against many queries, so the same single core answers {{num:sift_batch_speedup}}× more queries per second (SIFT; {{num:glove_batch_speedup}}× on GloVe). Adding all threads helps only a little more ({{num:sift_batchall_speedup}}× over one-at-a-time), most likely because the laptop's shared memory bandwidth, not arithmetic, becomes the limit again (I did not measure bandwidth directly). Interactive search sees one query at a time, which is why all QPS numbers below use that mode.

Why IVF-PQ never reaches high recall. Plain IVF-PQ stops at recall {{num:sift_pq_ceil}} (SIFT) and {{num:glove_pq_ceil}} (GloVe) however many lists are probed (Fig. 1, the green curves turn vertical). nprobe only controls which vectors are considered; the final top-10 is ranked by PQ's approximate distances, and with 4 dimensions per 8-bit sub-quantiser the quantisation error is larger than the gaps between the 10th and nearby neighbours, so true neighbours are found but mis-ranked. GloVe is worse because its neighbour distances are packed closer together (lower relative contrast), so the same error reorders more of them. Part 3 shows that exact re-ranking of a short candidate list removes this ceiling. HNSW and IVF-Flat reach recall ≥ 0.99 on both datasets (GloVe HNSW M = 8 stops lower only because the efSearch grid ends at 2048).

Part 3: Compression — PQ size and exact re-ranking (SIFT-1M)

Hypothesis (committed before the run, hypothesis.md). (1) The plain IVF-PQ recall ceiling rises with m (≈0.3/0.5/0.75/0.9 for m = 8/16/32/64) but never reaches 0.95; (2) re-ranking the top 100 with exact distances removes the ceiling for m ≥ 16 but not for m = 8; (3) re-ranking costs < 25% speed at a fixed nprobe, and re-ranked m = 16/32 beats IVF-Flat at recall 0.95; (4) re-ranking gives back almost all of PQ's memory saving. Hypothesis 3 only partly: re-ranked m = 16/32 do beat IVF-Flat at 0.95 (same nlist), but m = 64 does not; "< 25% cost" fails: median {{num:p3_cost_large_med}} at nprobe ≥ 8 but up to {{num:p3_cost_large_max}} (m = 8), and {{num:p3_cost_small}} at nprobe 1–4.

What happened. Relative contrast fell from {{num:p4_rc_d8}} to {{num:p4_rc_d128}} as d_int went from 8 to 128: in high intrinsic dimension the nearest neighbour is barely closer than a random point. Both indexes slowed down sharply, but HNSW collapsed faster: its QPS at 0.95 fell {{num:p4_hnsw_drop}} from d_int = 8 to {{num:p4_hnsw_last}}, IVF-Flat's {{num:p4_ivf_drop_same}} over the same range ({{num:p4_ivf_drop}} from 8 to 128). HNSW needed efSearch {{num:p4_hnsw_ef}} (distance computations per query ×{{num:p4_hnsw_ndis_ratio}}, {{num:p4_hnsw_ndis_first}} → {{num:p4_hnsw_ndis_last}}), and at d_int = 128 it reached only {{num:p4_hnsw_max_d128}} recall before costing more than exact search. IVF-Flat needed nprobe {{num:p4_ivf_np_d8}} → {{num:p4_ivf_np_d128}} of {{num:p4_nlist}} (×{{num:p4_ivf_ndis_ratio}} distances) and at d_int = 128 still reached 0.95 at {{num:p4_ivf_q_d128}} QPS by scanning {{num:p4_ivf_frac_d128}} of the data. The curves cross between d_int = 32 and 64: at 64, IVF-Flat gives {{num:p4_ivf_q_d64}} QPS against HNSW's {{num:p4_hnsw_q_d64}}. The control reproduced d_int = 16 almost exactly: {{num:p4_ctrl_same}}, recall within {{num:p4_ctrl_rec}} at every parameter, QPS at 0.95 within {{num:p4_ctrl_q95}}.

Mechanism. HNSW's greedy walk works when moving to a neighbour that is closer to the query reliably leads towards the answer. With low contrast every candidate looks about equally far, so the walk needs a very wide beam (large efSearch) to avoid dead ends: the distances HNSW computes grew {{num:p4_hnsw_step}} each time d_int doubled. IVF's worst case is bounded: at nprobe = nlist it is just a linear scan. Each IVF distance is a sequential, SIMD-friendly read (≈{{num:p4_ns_ivf}} ns per distance at d_int = 64), while each HNSW distance is a random memory access plus heap work (≈{{num:p4_ns_hnsw}} ns). So once HNSW must touch ~10% of the data (it touched {{num:p4_hnsw_frac_d64}} at d_int = 64) it loses. This also explains Part 2: the real datasets sit on this axis. SIFT's relative contrast ({{num:sift_rc}}) matches d_int ≈ 16, where HNSW wins by {{num:p4_ratio_d16}} on synthetic data and {{num:sift_ratio95}} on SIFT; GloVe's ({{num:glove_rc}}) lies between d_int = 32 and 64, where the gap closes, and on GloVe HNSW's lead at 0.95 shrinks to {{num:glove_ratio95}}.

Verdict: contrast prediction and control supported; IVF needing ≥ 25% of lists at d_int = 128 supported ({{num:p4_np_frac_d128}}); "IVF degrades faster, HNSW always faster" refuted, because HNSW degrades faster and loses from d_int = 64; d_int = 8 needed nprobe {{num:p4_ivf_np_d8}} (predicted ≤ 8). Not tested: larger M / efConstruction for HNSW at high d_int (which might delay the collapse), clustered rather than single-Gaussian data, other N, and IVF-PQ.

2. Costs. Build (all threads): HNSW {{num:hnsw_build_sift}} s (SIFT, M = {{num:hnsw_M_sift}}) and {{num:hnsw_build_glove}} s (GloVe, M = {{num:hnsw_M_glove}}), dominated by graph insertion, which grows with M; IVF-Flat ≈ {{num:ivf_build}} s, of which ≈ {{num:ivf_train}} s is k-means; IVF-PQ ≈ {{num:pq_build}} s, mostly k-means plus PQ codebook training. Memory per vector: HNSW {{num:hnsw_bpv}} B (raw floats + 2M neighbour ids on layer 0), IVF-Flat {{num:ivf_bpv}} B (raw floats + 8-byte id), IVF-PQ {{num:pq_bpv}} B (25–32-byte code + 8-byte id, so the id alone is a quarter to a third of the code size). PQ saves {{num:pq_saving}} memory (SIFT-1M in {{num:pq_mb_sift}} MB instead of {{num:full_mb_sift}} MB) and gives up exact distances. That caps recall ({{num:sift_pq_ceil}} / {{num:glove_pq_ceil}}), costs build time for training, and at large m costs speed too. Re-ranking recovers the recall only by keeping the raw vectors again (Part 3).

3. What the experiments imply. Headline numbers are properties of a dataset, not of an index. Part 4 shows the HNSW-vs-IVF ranking reverses as intrinsic dimension grows, so an "HNSW is {{num:sift_ratio95}} faster" result on SIFT says little about low-contrast data. Part 3 shows that "IVF-PQ fails at 0.95" and "PQ is {{num:pq_saving_sift_ivf}} smaller" are both true only for plain PQ: adding re-ranking flips the first and cancels the second. Headline numbers mislead when your data's contrast differs from the benchmark's, when the memory budget must also hold raw vectors for re-ranking, or when a different recall target moves the curves' crossing points.

4. 150K vectors or 10M, 100 ms, 16 GB. Exact one-at-a-time cost streams every vector once, so it grows linearly with N: {{num:sift_exact_ms}} ms for 1M SIFT vectors, and {{num:p4_exact_range}} ms measured at 200K in Part 4. 150K vectors: exact search takes ≈ {{num:est150k_ms}} ms and 77 MB, {{num:est150k_budget}} under budget with perfect recall and no build or tuning, so no ANN. 10M vectors: exact would take ≈ {{num:est10m_sift}} ms (SIFT-like) or ≈ {{num:est10m_glove}} ms (GloVe-like): over budget, so use ANN. Raw data is 5.1 GB (128-d); HNSW M = 16 at ~{{num:hnsw_bpv_sift}} B/vector needs ≈ {{num:hnsw10m_gb}} GB and fits in 16 GB with room for the build. I would use HNSW M = 16, efConstruction 200, efSearch tuned on held-out queries for recall ≥ 0.95 (≈ {{num:sift_hnsw_p95}}–{{num:sift_ef95_x2}} for SIFT-like data, sub-millisecond even at 10M since graph search grows slowly with N). For GloVe-like, low-contrast data I would use M = 32 and also try IVF-Flat (nlist ≈ 16K), since Part 4 shows IVF can win when contrast is low; both fit in memory and run far below 100 ms. These are extrapolations from 1M; 10M was not measured.
