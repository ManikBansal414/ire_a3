Setup

Data. SIFT-1M (128-d, Euclidean) and GloVe-100 (1,183,514 × 100, angular) from ann-benchmarks. GloVe vectors and queries are L2-normalised, so Euclidean distance ranks exactly like angular distance (‖a−b‖² = 2 − 2cos). Queries 0–4,999 are the tune half and 5,000–9,999 the test half. Selection rule. Every "at recall X" number is chosen on the tune half only: per build, the smallest efSearch/nprobe whose tune recall ≥ X; then the build with the highest tune QPS. Tables report that choice's test-half recall and QPS. Recall@10 is my own function: a returned id is a hit if its true distance (recomputed in float64 from the raw vectors, never the index's approximate distance) is ≤ the true 10th-neighbour distance, so ties at rank 10 are not mistakes; duplicates and −1 padding are handled (13 unit tests). Timing. One query per search call, FAISS and BLAS pinned to one thread, 50 warm-up queries, then 3 repeats over all 5,000 test queries (each repeat cycles the queries for ≥ 0.5 s); the median is reported. Builds use all {{num:threads}} hardware threads. Index size = bytes of faiss.serialize_index. Builds: HNSW M ∈ {8,16,32} (efConstruction 200); IVF nlist ∈ {1024, 4096}; IVF-PQ m = d/4 sub-quantisers × 8 bits (32 B/code SIFT, 25 B/code GloVe).

One-at-a-time vs batch. A single query is a matrix–vector product: to answer it the CPU must stream the whole 512 MB (SIFT) database from RAM and does only one multiply-add per float loaded, so it is limited by memory bandwidth ({{num:sift_one_ms}} ms per query). A batch turns the work into a matrix–matrix product (BLAS GEMM): each block of database vectors brought into cache is reused against many queries, so the same single core answers {{num:sift_batch_speedup}}× more queries per second (SIFT; {{num:glove_batch_speedup}}× on GloVe). Adding all threads helps only a little more ({{num:sift_batchall_speedup}}× over one-at-a-time), because the laptop's shared memory bandwidth, not arithmetic, is again the limit. Interactive search sees one query at a time, which is why all QPS numbers below use that mode.

Why IVF-PQ never reaches high recall. Plain IVF-PQ stops at recall 0.74 (SIFT) and 0.62 (GloVe) however many lists are probed (Fig. 1, the green curves turn vertical). nprobe only controls which vectors are considered; the final top-10 is ranked by PQ's approximate distances, and with 4 dimensions per 8-bit sub-quantiser the quantisation error is larger than the gaps between the 10th and nearby neighbours, so true neighbours are found but mis-ranked. GloVe is worse because its neighbour distances are packed closer together (lower relative contrast), so the same error reorders more of them. Part 3 shows that exact re-ranking of a short candidate list removes this ceiling. HNSW and IVF-Flat reach recall ≥ 0.99 on both datasets.

Part 3: Compression — PQ size and exact re-ranking (SIFT-1M)

Hypothesis (committed before the run, hypothesis.md). (1) The plain IVF-PQ recall ceiling rises with m (≈0.3/0.5/0.75/0.9 for m = 8/16/32/64) but never reaches 0.95; (2) re-ranking the top 100 with exact distances removes the ceiling for m ≥ 16 but not for m = 8; (3) re-ranking costs < 25% speed at a fixed nprobe, and re-ranked m = 16/32 beats IVF-Flat at recall 0.95; (4) re-ranking gives back almost all of PQ's memory saving. Setup. nlist = 1024 fixed, 8-bit codes, m ∈ {8,16,32,64}, each plain and with IndexRefineFlat (k_factor 10 → 100 candidates); nprobe swept as in Part 2. Only m and re-ranking change.

Results. (1) Ceilings were 0.38/0.57/0.73/0.88: close to the prediction, and none reach 0.95. Each doubling of m halves the dimensions per sub-quantiser and shrinks the distance error, but even 64-byte codes mis-rank about one in eight top-10 neighbours. (2) Re-ranking lifts the ceiling to 0.979/0.999/1.000 for m = 16/32/64 and only to 0.858 for m = 8. For m ≥ 32 the re-ranked recall at every nprobe equals IVF-Flat's to three decimals: the true neighbours are always inside the PQ top-100, so recall is limited only by which lists are probed. With m = 8 the codes are so coarse that some true neighbours rank below 100th among the candidates and are never re-scored. (3) At a fixed nprobe re-ranking costs only 3–18% (100 extra exact distances against 104–105 code scans). At recall 0.95, re-ranked m = 16 (1,933 QPS) and m = 32 (1,396) beat IVF-Flat (1,096 at the same nlist), because they scan 16–32-byte codes instead of 512-byte vectors. Not predicted: re-ranked m = 64 is slower than IVF-Flat (794 QPS). A PQ distance costs m scalar table lookups per code, while a float distance is a few SIMD fused multiply-adds, so beyond ~32 bytes scanning codes stops being cheaper than scanning raw floats. (4) Memory goes from 24.7 to 536.7 bytes/vector for m = 16: re-ranking needs the raw vectors, so the PQ saving survives only if those live on disk/SSD.

Verdict: hypotheses 1, 2 and 4 supported; 3 supported for m = 16/32 but wrong for m = 64.

Part 4: Own data — intrinsic dimension

What I changed. 200,000 base vectors + 10,000 queries, always 128-d, drawn from a Gaussian living in a random d_int-dimensional subspace (variance split evenly so E‖x‖² = 1 in every setting) plus small isotropic noise (total variance 0.001). Only d_int changes: 8, 16, 32, 64, 128 (128 = plain isotropic Gaussian). Control: d_int = 16 regenerated with a new seed, nothing else changed. HNSW (M = 16) and IVF-Flat (nlist = 512); sweeps, selection and timing as in Part 2; generator seeded. Hypothesis (committed first): relative contrast falls with d_int; both indexes need more work, but IVF-Flat degrades faster (neighbours scatter over Voronoi cells, nprobe ≥ 25% of nlist at d_int = 128) and HNSW stays faster everywhere; d_int = 8 needs efSearch ≤ 32 and nprobe ≤ 8; the control moves QPS by < 10%.

What happened. Relative contrast fell from 5.4 to 1.3 as d_int went from 8 to 128: in high intrinsic dimension the nearest neighbour is barely closer than a random point. Both indexes slowed down sharply, but HNSW collapsed faster: its QPS at 0.95 fell 108× from d_int = 8 to 64, IVF-Flat's 17× from 8 to 128. It needed efSearch 16 → 48 → 256 → 1536 (distance computations per query ×75, 339 → 25,440), and at d_int = 128 it reached only 0.90 recall before costing more than exact search. IVF-Flat needed nprobe 12 → 256 of 512 (×29 distances) and at d_int = 128 still reached 0.95 at 188 QPS by scanning 74% of the data. The curves cross between d_int = 32 and 64: at 64, IVF-Flat gives 235 QPS against HNSW's 158. The control reproduced d_int = 16 almost exactly: same efSearch and nprobe, recall within 0.007 at every parameter, QPS at 0.95 within 1–2%.

Mechanism. HNSW's greedy walk works when moving to a neighbour that is closer to the query reliably leads towards the answer. With low contrast every candidate looks about equally far, so the walk needs a very wide beam (large efSearch) to avoid dead ends, and the visited set grows roughly exponentially with intrinsic dimension. IVF's worst case is bounded: at nprobe = nlist it is just a linear scan. Each IVF distance is a sequential, SIMD-friendly read (≈37 ns per distance at d_int = 64), while each HNSW distance is a random memory access plus heap work (≈250 ns), so once HNSW must touch ~10% of the data it loses. This also explains Part 2: the real datasets sit on this axis. SIFT's relative contrast ({{num:sift_rc}}) matches d_int ≈ 16, where HNSW wins by 3–5×; GloVe's ({{num:glove_rc}}) lies between d_int = 32 and 64, where the gap closes. On GloVe, HNSW's lead at 0.95 shrinks to 1.9×.

Verdict: contrast prediction and control supported; IVF needing ≥ 25% of lists at d_int = 128 supported (50%); "IVF degrades faster, HNSW always faster" refuted, because HNSW degrades faster and loses from d_int = 64; d_int = 8 needed nprobe 12 (predicted ≤ 8). Not tested: larger M / efConstruction for HNSW at high d_int (which might delay the collapse), clustered rather than single-Gaussian data, other N, and IVF-PQ.

Part 5: Questions

1. Fastest at recall 0.95? HNSW on both: SIFT 4,910 QPS (M = 16, efSearch 64) vs IVF-Flat 1,493 (3.3×); GloVe 574 (M = 32, efSearch 384) vs 297 (1.9×). Exact search runs at 27 and 38 QPS. The winner does not change, but everything is ~8× slower on GloVe and the margin shrinks. GloVe has lower relative contrast and higher intrinsic dimension (LID {{num:glove_lid}} vs {{num:sift_lid}}), which forces larger efSearch/nprobe, and Part 4 shows HNSW is the more sensitive of the two to this. GloVe also needs the denser graph (M = 32), while SIFT is best with M = 16. IVF-PQ cannot reach 0.95 on either without re-ranking.

2. Costs. Build (all threads): HNSW 98 s (SIFT, M = 16) and 203 s (GloVe, M = 32), dominated by graph insertion, which grows with M; IVF-Flat ≈ 44 s, of which ≈ 30 s is k-means; IVF-PQ ≈ 65–73 s, mostly k-means plus PQ codebook training. Memory per vector: HNSW 656–672 B (raw floats + 2M neighbour ids on layer 0), IVF-Flat 409–522 B (raw floats + 8-byte id), IVF-PQ 34–42 B (25–32-byte code + 8-byte id, so the id alone is a quarter to a third of the code size). PQ saves 12–15× memory (SIFT-1M in 40 MB instead of 500–630 MB) and gives up exact distances. That caps recall (0.74 / 0.62), costs build time for training, and at large m costs speed too. Re-ranking recovers the recall only by keeping the raw vectors again (Part 3).

3. What the experiments imply. Headline numbers are properties of a dataset, not of an index. Part 4 shows the HNSW-vs-IVF ranking reverses as intrinsic dimension grows, so an "HNSW is 3× faster" result on SIFT says little about low-contrast data. Part 3 shows that "IVF-PQ fails at 0.95" and "PQ is 13× smaller" are both true only for plain PQ: adding re-ranking flips the first and cancels the second. Headline numbers mislead when your data's contrast differs from the benchmark's, when the memory budget must also hold raw vectors for re-ranking, or when a different recall target moves the curves' crossing points.

4. 150K vectors or 10M, 100 ms, 16 GB. Exact one-at-a-time cost is memory-bandwidth bound and linear in N: 37 ms for 1M SIFT vectors, and 5.6–6.5 ms measured at 200K in Part 4. 150K vectors: exact search takes ≈ 5–6 ms and 77 MB, 20× under budget with perfect recall and no build or tuning, so no ANN. 10M vectors: exact would take ≈ 370 ms (SIFT-like) or ≈ 220 ms (GloVe-like): over budget, so use ANN. Raw data is 5.1 GB (128-d); HNSW M = 16 at ~656 B/vector needs ≈ 6.6 GB and fits in 16 GB with room for the build. I would use HNSW M = 16, efConstruction 200, efSearch tuned on held-out queries for recall ≥ 0.95 (≈ 64–128 for SIFT-like data, sub-millisecond even at 10M since graph search grows slowly with N). For GloVe-like, low-contrast data I would use M = 32 and also try IVF-Flat (nlist ≈ 16K), since Part 4 shows IVF can win when contrast is low; both fit in memory and run far below 100 ms. These are extrapolations from 1M; 10M was not measured.

5. How this benchmark could mislead. (a) Timing noise on a laptop (turbo, thermal limits, background load). Tested: 3 repeats each ≥ 0.5 s; repeat spread was {{num:rep_spread_med}} (median) and {{num:rep_spread_p90}} (90th percentile). The Part 4 control moved QPS at 0.95 by only 1–2%, but single points at the same parameter differed by up to 38%. I report medians and also deterministic distance counts, and I treat speed differences below ~20% as ties. (b) Per-call Python overhead in the one-query-at-a-time loop inflates the cost of the fastest settings. Tested: an empty search call costs {{num:sift_overhead_us}} µs, ≤ 11% of the fastest measured query ({{num:min_ms_part2}} µs) and ≈ 2% at the fastest recall-0.95 setting (204 µs). Also checked: single-thread execution (CPU/wall median {{num:cpu_wall_med}}, max {{num:cpu_wall_max}}); no over-fitting of the tune-half selection (test minus tune recall {{num:tune_test_diff_mean}} on average); timed results identical to batched ones. Not tested: other machines, k ≠ 10, other efConstruction values, batch-mode throughput (which ranks indexes differently, Part 1), and data that does not fit in RAM.
